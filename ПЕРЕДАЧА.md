# Передача в продуктовую разработку

Сессия дизайн-системы закрыта 01.11.2026. Этот файл — всё, что нужно знать
следующей сессии, чтобы делать экраны «Глагола 2.0» по действующей системе.

## Версия и статус

**Glagol Design System 3.0.0.** Номер не поднимался: стандарт 01.11.2026
добавлен слоем и ничего в системе не переопределяет. Канонический номер —
поле `version` в `package.json`, другого нет.

**Готова для новых экранов.** Решения приняты, записаны с причинами, собраны
кодом и закрыты проверками. Работающие экраны продукта не тронуты.

## Где изменения

Ничего не слито в `main`. Три ветки, все отдельные:

| Репозиторий | Ветка | Верхний коммит | База | Что меняет |
| --- | --- | --- | --- | --- |
| `glagol-calendar` | `design/glagol-2-product-guard` | `c4f846f` | `afdd05e` | `app/ds3.css` (новый), `app/globals.css` (+6 строк), `scripts/ui-guard.mjs`, `scripts/sync-design.mjs` |
| `glagol-design-system` | `design/glagol-2-product` | `e4715f0` | `e8b9952` | документы, слой-копия, Design Lab, страница сверки, реестр решений |
| `glagol-atlas` | `design/glagol-2-product` | `0f39cb6` | — | съёмка на 375 и экраны дизайн-системы в атласе |

**Ветка календаря не трогает ни одного экрана.** Четыре файла, 752 строки, из
них 384 — новый `ds3.css`. Шесть строк в `globals.css` — это импорт слоя
рядом с `work.css`. Ни один работающий экран не меняется: весь слой лежит
внутри `[data-ds="3"]`, и это проверяется автоматически (`lab/build.mjs`
падает, если хоть один селектор вышел за область).

## Минимальный порядок интеграции

1. **Календарь первым.** Влить `design/glagol-2-product-guard` в рабочую
   ветку разработки. Сначала календарь, потому что хозяин `ds3.css` — он, и
   `sync-design` сверяет эталон с продуктом, а не наоборот.
2. **Обязательная проверка — полная сборка календаря** (см. ниже). Без неё
   интеграция не считается выполненной.
3. **Дизайн-система второй.** Влить `design/glagol-2-product` в `main`
   дизайн-системы. После этого `npm run sync-design` из календаря должен
   показать совпадение по одиннадцати файлам, включая `ds3.css`.
4. **Атлас — по желанию.** Ветка добавляет съёмку на 375 и экраны
   дизайн-системы. Мобильные эталоны после неё принимаются **глазами, по
   одному**: `npm run accept` не запускается не глядя.

Слияние выполняет Артём или сессия с его явного слова. Чужие рабочие ветки не
трогаются: на момент передачи календарь занят веткой `интеграция/этап-0`.

## Что обязательно проверить при интеграции

**Полную сборку календаря — `npm run build`.** В этой сессии она не
выполнялась: в worktree нет `node_modules`, а главный чекаут занят другой
сессией. Проверено иначе, и этого недостаточно для «готово»:

- `ds3.css` разобран `lightningcss` — тем самым движком, которым его
  разбирает Tailwind 4: ноль предупреждений;
- строка импорта ровно такая же, как у `work.css` и `panel.css` рядом в том
  же файле.

Дальше по списку, всё быстрое:

```bash
npm run check      # типы, сторож вёрстки, сверка эталона с продуктом
npm run ui-guard   # отдельно, если нужно только вёрстку
```

Сторож обязан **молчать** на существующем коде: правила стандарта спрашивают
только с нового и явно мигрированного. Если он заговорил на старых экранах —
это ошибка интеграции, а не повод чинить экраны.

## Ограничения, которые остаются

- **Существующие работающие экраны не меняем.** Ни ради соответствия, ни
  заодно.
- **Новые экраны создаём по действующей системе**, целиком и без исключений.
- **Старые приводим к стандарту при их последующей переработке** — на
  изменяемый раздел и затронутые им компоненты, не на весь экран.
- **Недостающие компоненты добавляем по мере необходимости**, а не впрок.
- **Три правила пока только описаны, кода нет** (`docs/COMPONENTS.md`,
  таблица «ждёт реализации»): поведение правки раздела полями на месте,
  «Сохранить / Отмена» на раздел и липкая шапка служебных экранов. Готовыми
  компонентами их называть нельзя.
- **Долг календаря, записанный замером:** 32 поля ввода с кеглем меньше 16
  (iOS зумит на них страницу) и `.work-btn` ростом 36 на телефоне. Чинится в
  рамках работы над теми же разделами.

## Как сделать первую страницу

Правило включается **признаком на корне экрана**. Больше ничего подключать не
нужно: слой уже импортирован в `app/globals.css` календаря.

```jsx
export default function Страница() {
  return (
    <main className="work" data-ds="3">
      <h1 className="work-title work-title--экран">Подготовка</h1>

      <div className="work-label">Мероприятие</div>
      <button className="work-btn work-btn--second">Назначить встречу</button>
      <button className="work-icon" aria-label="Закрыть">{/* svg 16 */}</button>
      <input className="work-field" placeholder="одной строкой" />
    </main>
  );
}
```

**Портал несёт оба признака.** `createPortal` и окна shadcn рисуются в
`<body>` мимо дерева экрана, и слой до них не достаёт — замерено: кнопка
13/700 с браузерной рамкой и без заливки, поле тринадцатым кеглем.

```jsx
createPortal(<div className="work" data-ds="3">…</div>, document.body)
```

Что даёт слой: кнопка 36 / 44 на телефоне, кегль 15 вес 600; круглая кнопка
36 с шагом касания 44; лестница кеглей 12 · 13 · 15 · 16 · 18 · 30; поле
ввода 16; отклик 0,96; ссылка подчёркнута всегда.

**Живой образец — `lab/новый-экран.html`**: плакат, разделы, кнопки трёх
видов, кружки, управление правкой, поля, плитки, чипы, ссылка и корень
портала. В его собственном `<style>` только раскладка — ни одного значения
системы. Если что-то непонятно словами, смотреть туда.
